## Findings

### F-01 — Full suite flaky under load — Important — window rc2–rc5

- Evidence: `npm test` baseline run fails with 5000 ms timeouts in
  `tests/regressions.test.ts` ("mipd: a higher single lab never gives a lower
  curve", case at `tests/regressions.test.ts:381`) and `tests/routes.test.ts`
  ("TC injection: exposure equals F·D/k3…", case at `tests/routes.test.ts:337`).
  Re-running those two files alone: 139/139 pass. Logs in
  `/tmp/opencode/hrt-1.6-rc-audit/test-baseline.log`.
- Impact: CI is not deterministic; a real regression can be hidden by a flaky
  timeout, and contributors learn to re-run rather than read failures.
- Fix idea: raise the timeout for those simulation tests or isolate them from
  parallel workers; add a repeat-run check. Verify with a clean full `npm test`.
- Status: fixed in rc2. `vitest.config.ts` now sets `testTimeout: 15_000`, so
  the simulation-heavy cases keep their default parallel scheduling without
  hitting the 5 s limit under load. Two consecutive full runs are green (105
  files, 1031 passed, 4 expected fail; 88 s and 76 s). tsc, lint, format and
  version checks are green.

### F-02 — rc tags and version strings unsupported by release tooling — Important — window rc2–rc5

- Evidence: `scripts/set_version.py:114` `--update` uses
  `re.fullmatch(r"\d+\.\d+\.\d+", …)` so it cannot write `1.6.0-rc.1`;
  `.github/workflows/release.yml:7-10` matches tags `v[0-9]+.[0-9]+.[0-9]+`, so
  `v1.6-rc1` … `v1.6-rc10` do not trigger a publish. `set_version.py --check`
  still accepts the rc string because it only compares fields.
- Impact: rc stages cannot be version-bumped by the standard tool and cannot
  accidentally publish — the latter is desirable, the former is a workflow gap.
  Docs now warn agents not to "fix" the tag pattern to publish an rc.
- Fix idea: add explicit prerelease support to the script and a separate
  pre-release workflow only if the team wants rc artifacts; otherwise formalize
  the manual bump used in rc1 as the supported path.
- Status: fixed in rc2 by formalizing the manual bump as the supported rc path.
  `docs/AI-GUIDE.md` and `wiki/AI-Contributors.md` now list the six version
  fields (`package.json`, both `version` entries in `package-lock.json`,
  `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, and the app package in
  `src-tauri/Cargo.lock`) and require `python3 scripts/set_version.py --check`
  after editing them. The `--update` regex and the `release.yml` tag pattern are
  intentionally unchanged so rc tags still cannot publish. Guarded by
  `tests/rcVersionPolicy.test.ts`. Verification: targeted 2/2, full suite
  (106 files, 1033 passed, 4 expected fail), tsc/lint/format/version green.

#### F-09 — Optional research models wired into the default simulation result — Important — window rc2–rc5

- Evidence: `src/domain/simulation/runSimulation.ts:262-282` always computes
  `concNGdL_T_free`, `concPGmL_E2_free`, and `concPGmL_E2_bioavailable` and

- Fix idea: choose one contract — gate every new output behind named flags and

### Findings from the security / privacy deep review

A separate read-only review of auth, sessions, WebAuthn, rate limiting, share
crypto, raw HRT transport, deployment, and desktop config found **no Critical**
issues and confirmed substantial existing hardening (see Coverage notes). Five
substantiated findings follow; exploitability caveats are stated explicitly.
The reviewer's duplicate observations about F-18 (debug logging) and the
TOTP/CORS/decompression/E2EE controls were checked and need no new entry.

#### F-22 — Rate limiting fails open when a binding is missing or throws — Important — window rc2–rc5

- Evidence: `src/server/rateLimit.ts:17-34` returns `true` (allow) both when a
  rate-limit binding is absent (`:20-27`) and when `limiter.limit()` throws
  (`:31-34`); `passwordCheckAllowed()` at `:13-15` inherits the same behavior.
  Top-level throttling (`worker.ts:432-470`) and route-local throttles (e.g.
  `src/server/routes/public.ts:31,108,131,156,236,268,303`,
  `sharesAccess.ts:64,94,146`, `auth.ts:369-430`) all depend on it.
  `wrangler.toml:51-74` defines the five bindings, so this is not attacker-
  triggerable in the intended Cloudflare deploy; it is a fail-safe defect.
- Impact: a deploy misconfiguration or a temporarily throwing binding removes
  most online throttling silently. Login and share-password have independent
  persistent backoff (`auth.ts:148-193`, `sharesAccess.ts:139-165`), and admin
  reauth calls `passwordCheckAllowed()` (`admin.ts:54-62`) but inherits the
  fail-open path. Passkey option/verify, registration, F2F/HRT/tool routes, and
  trusted-IP creation have no route-local throttle.
- Fix idea: fail closed (503/429) on limiter errors; validate required bindings
  at startup; add a D1/in-memory fallback for self-hosting; test that a missing
  or throwing limiter does not disable protection.
- Status: fixed in rc2 (`src/server/rateLimit.ts`, `worker.ts`). A missing
  binding now uses a per-env, per-isolate 60 s sliding-window memory limiter;
  a throwing binding denies the request. `tests/rateLimit.test.ts` covers the
  missing-binding limit, thrown-limiter denial, `passwordCheckAllowed`, and
  per-env isolation. Verification: 4/4 targeted tests and the full suite
  (98 files, 1008 passed, 4 expected fail) are green.

#### F-23 — Unauthenticated raw HRT `pair.start` can exhaust pairing state — Important — window rc2–rc5

- Evidence: `hrt-server/server.mjs:478-493` forwards `pair.start`/`pair.poll`
  to the Worker without the device proof-of-possession check applied to normal
  `request` operations (`:538-558`); the raw TLS listener binds `0.0.0.0`
  (`:379-386,630-640`). `hrtPairing.ts:18-22` sets `PAIR_LIMIT=10`,
  `HOLD_SECONDS=3600`; `:287-347` holds/over-limit callers receive a fake
  success; `:349-359` creates a pairing row even for a null user lookup;
  `:492-500` retention only filters the user-visible list, with no deletion.
  `worker.ts:928-955` sweeps sessions/shares/challenges/F2F but not HRT pairing.
- Impact: any TLS client can spam `pair.start` for an arbitrary username,
  putting that username in a one-hour hold (repeatable denial of new pairing),
  and accumulate `hrt_pair_requests`/`hrt_holds` rows without a deletion path.
  This is **not** account takeover: approval still needs the 128-hex device
  code (`hrtPairing.ts:524-542`).
- Fix idea: require device proof, proof-of-work, or per-source-IP throttling
  for `pair.start`/`pair.poll`; cap pending/held rows; add scheduled cleanup of
  expired pairing rows and stale holds.
- Status: fixed in rc2. `hrt-server/server.mjs` now applies a per-source-IP
  60-second sliding-window limit to unauthenticated `pair.start` frames
  (default 10/min, `HRT_PAIR_STARTS_PER_MINUTE`); excess frames get
  `RATE_LIMITED` and are not forwarded. `hrtPairing.ts:sweepHrtPairing()` is
  called from the Worker's scheduled handler to delete pairing rows and holds
  older than the existing 12-hour retention window, so state no longer
  accumulates forever. `pair.poll` remains unthrottled: it is read-only and
  requires the 256-bit poll secret. Verification: targeted tests 17/17,
  full suite 98 files / 1010 passed / 4 expected fail, tsc/lint/format clean.

#### F-24 — HRT trusted-IP password recheck has no throttle — Important — window rc2–rc5

- Evidence: `hrtPairing.ts:685-700` calls `bcrypt.compare(password,
user.password_hash)` after only shape validation, with no
  `passwordCheckAllowed()`, IP check, or persistent lockout. `worker.ts:649-661`
  authenticates `/api/hrt/` web routes but applies no route-local rate limit,
  and `:433-439` excludes `/api/hrt/` from the sensitive-path list. Every other
  password recheck uses the shared bucket (`userProfile.ts:62,106`,
  `twoFactor.ts:77,147,196`, `passkeys.ts:161,230`, `admin.ts:58`).
- Impact: a stolen session gets an online password oracle limited only by
  bcrypt cost; success adds a trusted IP, which suppresses the pairing hold
