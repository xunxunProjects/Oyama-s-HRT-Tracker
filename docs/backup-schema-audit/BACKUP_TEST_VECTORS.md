**Status:** documentation only. No schema, `formatVersion`, Tools, Docker, or
License code was changed in this work item. Website code changes referenced here
are the complete-backup review fixes on `agent/add-gpg-website`.

`2b9c856` adds `tools/hrt-tool`; the `tools/hrt-cold` code is unchanged since
`0511d05`.

The Tools `hrt-cold` validator checks the hand-off envelope and container
shapes; it does **not** validate clinical record semantics or apply restore
rules. The website importer remains authoritative for record validation, merge
behavior, and conflicts. The vectors below were derived by reading both
implementations; they are not a cross-language conformance run and no Tools
tests were executed for this document.

Tools can now sign the plaintext bundle and verify it against a pinned key.
The signature lives inside the encrypted payload, so the envelope and `.hrtb`
bytes are unchanged. A verified Tools decrypt also keeps a local replay
high-water mark. The website's direct plaintext import remains unauthenticated:
it has no keys or signature to check.

**Authority is path-dependent**

- **TOOLS AUTHORITATIVE (hand-off/container)** — the envelope, `.hrtb`
  container, duplicate-key/depth limits, and OpenPGP encrypt/decrypt/inspect
  rules define whether Tools will accept or encrypt a file. A website parser
  being more permissive does not make the input valid for Tools.
- **WEBSITE AUTHORITATIVE (restore semantics)** — once an envelope is accepted,
  the website decides record validation, tombstone bounds, merge, conflict,
  preference, and scalar behavior. Tools accepting a file does not mean the
  website will restore every record.
- **UNRESOLVED** — the two sides disagree on an interface/product decision, or
  no decision exists; do not claim parity until it is decided in a separate
  approved work item.

## Source account

A bundle exported while signed in carries an optional top-level
`sourceAccount`: the lowercase hex SHA-256 of
`oyama-hrt-complete-backup/account/<account id>`. It holds neither the account
id nor the username. On import the website compares it with the same hash of
the signed-in account, and the confirmation says whether the file came from
this account or from another one. A file without the field (exported signed
out, or by an older version), or a device that is signed out, gets the plain
"make sure this backup is yours" check, and a malformed value is ignored. The
tag catches the wrong file; it is not a signature and proves nothing about who
wrote the file, which stays the Tools signing path's job. Tools accepts unknown
envelope fields, so `formatVersion` stays 1.

## Review-fix notes (website)

- Expired local tombstones no longer block resurrection of an older incoming
  record; the pruned map is written back during the same merge, so a later sync
  reading the stored tombstones cannot re-delete the restored record.
- Record ids reject every own property name of `Object.prototype`
  (`toString`, `valueOf`, `hasOwnProperty`, `__proto__`, `constructor`, and the
  rest) plus `prototype`. Sync tombstone maps are null-prototype objects and
  every tombstone/id lookup uses `Object.hasOwn`, so an inherited value is
  never read as a deletion.
- The preview fingerprint includes the target owner/account. If the signed-in
  account changes while the confirmation dialog is open, re-previewing produces
  a different fingerprint and forces the dialog to show the new target.
- The complete-backup plan loader now accepts the same syntactically valid
  drug codes as bundle validation. An unknown code is preserved, treated as an
  unmodelled drug, and is not rewritten to a known ester.
- Export now shares the importer's entry limit, duplicate-id rejection,
  future-stamp bound, and one cross-version ester rule. Invalid records,
  duplicate ids, and dropped tombstone/stamp entries are reported.
- A preferences-only bundle is reported as "settings only" instead of failure.
  A merge with every category blocked reports nothing applied and does not
  claim success.
- Same-bundle record + tombstone contradictions are reported in the preview.
- Case-variant envelope keys and duplicate JSON keys remain parser-level
  differences; no case-insensitive fallback is added.

## Acceptance status

- These vectors document current code, not approved parity.
- BTV-1, BTV-2, BTV-4, BTV-5, BTV-6, BTV-8 to BTV-17 have a designated
  authoritative side above.
- BTV-3 and BTV-7 remain **UNRESOLVED** product/interface decisions.
- Export, preview, merge, account targeting, rollback, failure paths, and
  reload/re-export equality now have browser L3 coverage in `e2e/`. That is
  automated local evidence, not production restore.
- Complete-backup Replace is a separate danger action. It refuses incomplete
  bundles, writes one recovery journal before touching records, rolls back on a
  failed write, and replays or finishes the journal at the next app start.
  `e2e/replace.spec.ts` covers success, refusal, rollback, and both recovery
  phases. The journal needs free localStorage headroom for the target data;
  if it cannot be written, Replace aborts before touching records. This is an
  application-level transaction over localStorage, not a
  browser primitive; no production-restore claim is made.
- No claim is made about production readiness, OpenPGP key handling, License
  Gate approval, or Docker.
